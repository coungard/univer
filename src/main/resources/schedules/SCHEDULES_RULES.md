# Разбор расписаний перед миграцией

Текстовые расписания в этой папке (например, `ktie_kurs1_nedeli1-3.txt`) переносятся в БД миграциями
Flyway (`db/migration/data/schedules/`). Файлов расписаний будет много, но правило их разбора перед
миграцией — одно и то же для всех, поэтому оно вынесено сюда отдельным документом, а не хранится внутри
каждого конкретного текстового файла расписания.

Легенда: [✅ решено] — уже сделано и лежит в `src/main/resources/db/migration/data/`;
[⏳ открыто] — требует решения/данных, прежде чем писать очередную миграцию с самим расписанием
(Course/Pair).

## Структурные пробелы модели (нужны изменения схемы, не просто данные)

1. [✅ решено, GitHub issue #42] Подгруппы (`п/гр`) не существуют нигде в модели. Половина лабораторных
   расписана по подгруппам с разной чётностью недели («2нед-1п/гр, 4нед-2п/гр»). Решили не делать
   структурную поддержку (никаких новых полей/сущностей у Student/Pair/Group) — вместо этого условие
   подгруппы записывается свободным текстом в уже существующее поле `Lecture.content`, точечно, при
   генерации конкретной лекции из Pair на дату, если для неё было деление по подгруппам.

2. [✅ решено, GitHub issue #47] Тип занятия (`лк`/`пз`/`лб`) и форма контроля (`зач`/`экз`) нигде не
   хранятся — ни у Course, ни у Pair такого поля нет (в отличие от `room`, который уже добавили в
   Сценарии 3). Решили не делать структурную поддержку (никаких новых полей у Course/Pair) — вместо
   этого тип занятия и форма контроля записываются свободным текстом в уже существующее поле
   `Lecture.content`, точечно, при генерации конкретной лекции из Pair на дату.

3. [✅ решено, GitHub issue #49] Реального «звонкового» расписания времени пар в файле нет — только
   «Пара: 1»..«Пара: 4», без часов. В Сценарии 3 время 08:00–09:30 было иллюстративным предположением,
   не подтверждённым реальным bell-schedule. Решили: добавлен справочник `BellScheduleEntry`
   (номер пары → время начала/окончания), per-university (см. TARGET.md про конфигурируемую сетку
   времён). Это только источник для заполнения `Pair.startTime`/`endTime` при создании пары — сами
   эти колонки остаются самостоятельными редактируемыми (перенос конкретного занятия по-прежнему
   возможен явным указанием времени). Засеяно реальное расписание звонков ДГТУ (6 пар).

4. [✅ решено, GitHub issue #48] Заголовок «1-3 недели» противоречит содержимому — внутри таблицы есть
   ссылки на «2нед»/«4нед» (чётные) для подгрупп. Решили: в приоритете диапазон недель из заголовка
   (1-3) — схему WeekParity под это не меняем. Если для конкретной ячейки таблица указывает
   конфликтующие «2нед»/«4нед», это условие недели уточняется свободным текстом в `Lecture.content`
   той лекции, а не структурно.

5. [✅ решено, GitHub issue #46] Ячейки вида «51 Ин.яз, ... / 252 Ин.яз, ...» (через слэш) — два
   параллельных занятия для двух подгрупп в одном слоте (разные кабинет+препод). Следствие решения по
   пункту 1 — раз структурной поддержки подгрупп нет, такие ячейки тоже не парсятся в отдельные
   Pair/Lecture, а записываются одной строкой в `Lecture.content`, как обычные подгруппы.

6. [✅ решено] Расписания приходят парами файлов вида `..._nedeli1-3.txt` / `..._nedeli2-4.txt`, чьи
   заголовки формально пересекаются на общей неделе (здесь — неделя 3). Это не два диапазона недель, а
   чередование нечётных (1, 3) и чётных (2, 4) недель семестра — то есть ровно `WeekParity.ODD` и
   `WeekParity.EVEN`. Файл `*_nedeli1-3.txt` мигрируется с `week_parity = ODD`, `*_nedeli2-4.txt` — с
   `week_parity = EVEN`, на одни и те же уже созданные первым файлом StudyYear/Semester/Group/
   WeekScheduleCycle (второй файл не создаёт их заново). Уточнить у пользователя перед миграцией
   каждой новой такой пары файлов, если нумерация недель в заголовках не «1-3»/«2-4» буквально.

## Организация файлов: университет и учебный год

Модель изначально многовузовая (`University` — корневой агрегат, `BellScheduleEntry` уже per-university,
issue #49), поэтому расписания в этой папке и соответствующие им миграции организованы по университету
и учебному году, а не лежат плоским списком — иначе по мере роста числа вузов/годов станет невозможно
понять из одного имени файла, к чему он относится.

Схема вложенности (факультет по-прежнему часть имени файла, как и раньше, — `ktie`, отдельный уровень
вложенности под него не нужен):

```
schedules/<university-slug>/<YYYY-YYYY>/<faculty-slug>_kursN_nedeliA-B.txt
db/migration/data/schedules/<university-slug>/<YYYY>/V##__insert_<faculty-slug>_full_week_schedule[_even].sql
```

Обратите внимание: год форматируется по-разному в двух деревьях — это осознанно, у них разный смысл.

- `<university-slug>` — транслитерация краткого имени университета в нижнем регистре, той же
  стилистики, что и `ktie` для факультета (для ДГТУ — `dgtu`). Это чисто файловая конвенция: у
  `University` нет и не заводится отдельное поле `code` под неё — маппинг слуг на университеты описан
  только здесь, в этом документе.
- `<YYYY-YYYY>` (`.txt`-источники) — учебный год документа целиком (осень+весна), например
  `2025-2026` для расписания, действующего с осени 2025.
- `<YYYY>` (Flyway-миграции) — год `Semester.start_date` конкретного семестра, который заводит эта
  миграция (например, `2026` для `AUTUMN`-семестра с `start_date = '2026-09-01'`). Одна миграция
  почти всегда заводит один семестр — используется календарный год его начала, а не диапазон
  учебного года; если для одной и той же группы позже добавится весенний семестр того же учебного
  года (например, `SPRING` со `start_date` в начале 2026 — уже другой календарный год, чем осенний
  `2025`), его миграция попадёт в свою `<YYYY>`-папку по фактическому году её `start_date`, даже если
  учебный год у обоих семестров один и тот же.
- Flyway рекурсивно сканирует `classpath:db/migration/data` (см. `spring.flyway.locations` в
  `application.yml`) — вложенность в `data/schedules/<university>/<year>/` работает без изменений
  конфигурации, как уже сегодня работает `data/schedules/`.
- **Нумерация `V<n>` остаётся общей на весь Flyway** независимо от вложенности (см. CLAUDE.md) —
  следующая новая миграция расписания использует следующий свободный номер по всему репозиторию
  (`schema/` + `data/`, включая все подпапки `data/schedules/**`), а не отдельную нумерацию «с V1» внутри
  подпапки конкретного университета/года.
- **Перемещение уже применённой Flyway-миграции в новую подпапку — проверено безопасно.**
  `flyway_schema_history` матчит миграции по версии и чек-сумме содержимого, не по пути обнаружения —
  проверено локально (`mvn spring-boot:run` против БД, где расписание уже было применено по старому
  плоскому пути `db/migration/data/schedules/`): после переноса под `dgtu/<год>/` без изменения
  содержимого Flyway отработал штатно (`Successfully validated N migrations`, `Schema "public" is up
  to date`), без ошибок валидации или повторного применения.

- **Расписание 2025-2026 учебного года (`dgtu/2025/`) удалено.** При пересборке всего набора Flyway-
  миграций без `ALTER TABLE` (см. `migration.txt` в корне `resources/`, п.11) устаревшее расписание
  за прошлый учебный год было убрано целиком, а не перенумеровано — оно на момент переписывания было
  неактуально и не нужно было сохранять как историю. `study_years`/`courses`, которые оно раньше
  заводило первым (и на которые ссылалось расписание следующего года как на «переиспользуемые»),
  перенесены в расписание 2026-2027 — см. пример ниже.

### Пример: расписание того же курса на следующий учебный год (V11/V12)

`V11__insert_ktie_full_week_schedule.sql`/`V12__insert_ktie_full_week_schedule_even.sql`
(`dgtu/2026/`) — единственное на данный момент расписание курса КТиЭ 1 курса, заводит всю цепочку
`StudyYear -> Semester -> Group -> WeekScheduleCycle -> Course -> Pair` с нуля (аналогично тому, как
это раньше делало ныне удалённое расписание `dgtu/2025/`). Показывает, что переиспользуется между
файлами одного и того же расписания, а что заводится заново:

- **Переиспользуется** (те же `id`, одна и та же строка): `programs`, `teachers` — заведены отдельными
  миграциями (`V2`/`V3`) и не зависят от конкретного расписания; `study_years`/`courses`, заведённые
  в `V11`, переиспользуются в `V12` (том же учебном годе) без повторной вставки — `study_years` в
  принципе не может дублироваться: `UNIQUE(program_id, year_number)`, «курс 1 программы X» одна запись
  на всю систему, календарная привязка к году живёт в `Semester`, не в `StudyYear`.
- **Заводится заново при переходе на следующий учебный год** (если/когда появится, например,
  `dgtu/2027/`): `semesters` (новый `start_date`/`end_date`), `week_schedule_cycles` (1:1 к новому
  семестру), `student_groups` (новый `semester_id`, те же названия групп), `pairs` (новый
  `week_schedule_cycle_id`, ссылки на переиспользуемые `course_id`/`teacher_id` не меняются) —
  `study_years`/`courses`/`programs`/`teachers` по-прежнему переиспользуются как есть.
