# Скрипты для наполнения БД вузами России (issue #73)

Данные генерируются в две Flyway data-миграции двумя скриптами — читайте их в этом порядке.

## 1. generate_universities_migration.py → V17__insert_universities_data_rf.sql

Наполняет `public.address` / `public.universities` 485 вузами из 700, у которых в
explore/*.md был проверенный сайт. Существующую запись ДГТУ (`V2__insert_universities_data.sql`)
не трогает — миграция чисто аддитивная.

## 2. generate_remaining_universities_migration.py → V19__insert_universities_data_rf_remaining.sql

Добавляет оставшиеся 215 вузов — тех, для кого сайт (и, соответственно, email) на момент
генерации V17 не был известен. Стало возможным после
`V18__make_address_email_nullable.sql` (`ALTER TABLE address ALTER COLUMN email DROP NOT NULL`):
раньше такие вузы приходилось либо пропускать, либо выдумывать им email, теперь строка
адреса просто сохраняется с `email = NULL` (и `website = NULL`, если сайт неизвестен).

Скрипт переиспользует парсер и справочник городов из `generate_universities_migration.py`
(импортирует его как модуль) — ничего не дублирует и не меняет в уже сгенерированном V17.

## Источник исходных данных

`explore/*.md` — 700 файлов, по одному на вуз/филиал, подготовленных вручную в несколько
проходов (см. историю коммитов) на основе ru.wikipedia.org и открытых справочников вузов
(конкретные ссылки — в разделе «Источники» каждого файла). Каждый файл содержит
структурированные поля: Полное название, Сокращённое название, Город, Год основания,
Тип, Ректор, Адрес, Сайт, Число студентов — поле, где данных не нашлось, помечено как
«информация требует уточнения» и скрипты трактуют его как отсутствующее (NULL), а не
пытаются его домыслить.

## Регион по городу

Схема требует `address.region` NOT NULL, а в explore/*.md регион явно указан не всегда
(например, «Барнаул» без пометки «Алтайский край» — сам город однозначно определяет
регион). Поэтому регион берётся из справочника `CITY_REGION` в `generate_universities_migration.py`
— вручную составленного соответствия «как записан город в explore/*.md» → «(нормализованный
город, регион)», построенного по всем уникальным значениям поля «Город», встретившимся в
explore/. Это объективные, проверяемые географические факты (какой город к какому
субъекту РФ относится), а не придуманные для конкретного вуза данные.

## Email

`address.email` больше не NOT NULL (V18), но выдумывать его всё равно не вариант (issue
#73: «если по вузу нет данных для необязательных полей — оставлять NULL... если email
обязателен, а достоверного адреса нет — такой вуз либо пропустить, либо использовать email
с официального сайта вуза»). Поэтому:
- для 485 вузов с проверенным сайтом (V17) email формируется по общепринятому шаблону
  `info@<домен сайта>` — сам домен настоящий (взят из подтверждённого источника), а вот то,
  что почтовый ящик `info@` на нём действительно существует и работает, отдельно не
  проверялось;
- для 215 вузов без проверенного сайта (V19) email оставлен `NULL`, а не придуман.

## Адрес / улица / индекс

Поле «Адрес» в explore/*.md, когда оно известно, обычно в формате
`[индекс, ]г. Город, Улица, д. N`. Скрипты регуляркой ищут «г. Город» и по нему делят
строку на индекс (то, что было до) и улицу (то, что после). Для вузов без известного
подробного адреса `address`/`street` заполняются как `г. {Город}` — это не выдуманный
адрес, а просто менее детальный (город и регион при этом корректны).

## Запуск и повторный запуск

```bash
py scripts/generate_universities_migration.py
py scripts/generate_remaining_universities_migration.py
```

Оба скрипта **отказываются перезаписывать уже существующий выходной файл** (V17 / V19
соответственно) без флага `--force` — CLAUDE.md запрещает редактировать уже
закоммиченную/применённую Flyway-миграцию, а повторный запуск без этой защиты пересоздал
бы файл с новыми случайными UUID, что было бы именно такой правкой. `--force` — только для
осознанного пересбора миграции, которая точно ещё нигде не применялась.

Если позже добавится вуз в городе, которого ещё нет в `CITY_REGION`, оба скрипта
остановятся с ошибкой `неизвестный город ..., добавьте его в CITY_REGION` — это осознанно,
чтобы регион не заполнялся наугад.

## Факультеты/институты (продолжение issue #73)

Ручной веб-поиск по вузу (которым собирался explore/*.md) не масштабируется на факультеты —
упирается в лимит веб-поиска за сессию. Вместо этого — прямые HTTP-запросы (без веб-поиска)
к агрегатору ucheba.ru, у которого на каждый вуз есть страница `/uz/{id}/units` со списком
факультетов/институтов. Три скрипта запускаются по очереди:

```bash
py scripts/build_ucheba_id_index.py          # -> scripts/ucheba_id_index.jsonl
py scripts/match_universities_to_ucheba.py   # -> scripts/university_aggregator_mapping.json
py scripts/fetch_faculties_ucheba.py         # -> explore/faculties/<slug>.md
py scripts/generate_faculties_migration.py   # -> V<n>__insert_faculties_bulk.sql
```

1. `build_ucheba_id_index.py` проходит по всем ID из sitemap ucheba.ru (`/uz/{id}`,
   ~5000 записей, не только вузы) и лёгким partial-запросом (`Range: bytes=0-4095`) достаёт
   `<title>` каждой страницы — этого достаточно, чтобы узнать название, полную страницу
   (250-350 КБ) грузить не нужно. Результат кэшируется построчно в JSON Lines, чтобы можно
   было безопасно докачивать/перезапускать.
2. `match_universities_to_ucheba.py` сопоставляет 700 вузов из explore/*.md с этим индексом
   по названию. **Только точные совпадения используются дальше** — нечёткое (fuzzy)
   сопоставление показало систематические ложные совпадения на сетях филиалов (РАНХиГС/РЭУ/
   ФСБ — разные региональные филиалы схлопывались в одну и ту же страницу источника из-за
   почти идентичных названий, отличающихся только городом) и результат в json хранится только
   для прозрачности/будущей ручной проверки, `fetch_faculties_ucheba.py` их по умолчанию
   игнорирует (см. `--include-fuzzy`). Отдельно проверяется неоднозначность коротких названий
   — аббревиатуры не уникальны (например «МГПУ» — это и Московский, и Мордовский
   педагогические университеты); совпадение по краткому названию принимается только когда оно
   однозначно и с нашей стороны (по всем 700 вузам), и со стороны индекса ucheba.ru.
3. `fetch_faculties_ucheba.py` идёt по страницам `/uz/{id}/units` с пагинацией (`?page=N`) и
   вычленяет из HTML названия подразделений — они оканчиваются названием вуза, но падеж может
   отличаться от именительного (см. код: сравнение по стеммам слов, не по точному суффиксу).
   Где не собралось всё (крупные вузы отдают под сотню подразделений на нескольких страницах)
   или данных не нашлось вовсе — явная пометка "требует уточнения" с указанием, сколько
   собрано из скольки заявлено.
4. `generate_faculties_migration.py` находит `university_id` по уже накопленным data-миграциям
   (парсит `INSERT INTO public.universities`), приоритет — полное название (`description`),
   короткое (`name`) — только если оно однозначно во всей БД. Дедуплицирует по
   `UNIQUE (name, university_id)` и пишет следующий свободный номер миграции.

Из 700 вузов через ucheba.ru безопасно сматчено 71 (только точные совпадения), из них
реальные данные собраны для 42.

## Второй источник — postupi.online

У ucheba.ru нет отдельных страниц на региональные филиалы сетевых вузов (проверено вручную
на РАНХиГС — все 16 найденных записей оказались внутренними подразделениями головного
московского кампуса, ни одного регионального филиала). У postupi.online — есть (например,
`filial-yufu-v-gelendzhike` — отдельная страница Геленджикского филиала ЮФУ), поэтому это не
повтор той же попытки, а действительно другой охват. Два дополнительных скрипта:

```bash
py scripts/build_postupi_id_index.py         # -> scripts/postupi_id_index.jsonl
py scripts/match_universities_to_postupi.py  # добавляет postupi_url в university_aggregator_mapping.json
py scripts/fetch_faculties_postupi.py        # -> explore/faculties/<slug>.md (только новые)
```

`build_postupi_id_index.py` идёт по ~85 страницам-каталогам из
`sitemap_vuzy.xml` (у postupi.online нет прямого sitemap по вузам, только по категориям
специальностей) с пагинацией `?page_num=N`, вытаскивая пары (URL вуза с региональным
поддоменом, название) — один вуз может встретиться в нескольких категориях, дедуплицируется
по URL. `match_universities_to_postupi.py` обрабатывает только вузы, не получившие точное
совпадение на ucheba.ru, с теми же защитами от неоднозначности (полное название в
приоритете, короткое — только если однозначно с обеих сторон). `fetch_faculties_postupi.py`
не трогает вузы, у кого уже есть файл в `explore/faculties/` (с ucheba.ru).

**Итог обоих источников**: из 700 вузов сматчено 399 (71 — ucheba.ru, 328 — postupi.online),
реальные данные о факультетах/институтах собраны для 289 (1379 записей,
`V20__insert_faculties_bulk.sql`). Оставшиеся ~300 (в основном — маленькие
специализированные вузы/семинарии/академии, которых нет ни в одном из двух агрегаторов, и
вузы, чьи fuzzy-совпадения были отфильтрованы как небезопасные) — предмет будущей работы, не
выдумываем сопоставление там, где не уверены.
